## 背景

本次体检发现 1 个高危安全问题（SSH 私钥明文落库）、5 个中低危问题、6 项性能问题。仓库整体工程质量良好（架构分层清晰、SQL 标识符引用规范、密钥体系设计到位、终端渲染已是 damage 增量管线），本次修复按"先堵漏，再修慢"原则收口。

## 兼容性策略：方案 A（推迟启动期迁移）

### 背景

A1 把 `is_sensitive_field` 扩展到包含 `ssh_private_key` 等字段，新写入路径会自动加密；
但存量数据库里仍存在**明文 SSH 私钥**。直接接入启动期迁移函数会引入兼容性风险：

- **字段级加密**（`encrypt_json_passwords` 用 `crypto::encrypt_password`）走**本地主密钥槽**（`ENCRYPTION_KEY_V3`，Argon2id 派生）
- 与 sync_server envelope 用的 sync master_key 是**两套独立密钥**，互不影响
- 老客户端（commit < `7b36af88` 的 V3 派生槽引入前版本）没有 `ENCRYPTION_KEY_V3` 槽
  - 读 ENC:V3 字符串 → `decrypt_password` 返回空串 → **SSH 私钥丢失**
- 风险场景：新客户端写入 ENC:V3 → 同步到云端 → 老客户端从云端拉 → 丢私钥

### 方案 A 的取舍

- **新写入路径已加密**（用户每次新建/编辑连接，ssh_private_key 自动变密文）✓
- **存量明文暂不动**：函数 `migrate_encrypt_existing_sensitive_fields` 已实现并测试通过，
  但**当前不接入**任何调用链（确认 grep 无调用点，仅在注释中提及）
- **等待窗口期**：建议 1-2 个月后所有客户端升级到 ≥ `7b36af88`，再接入迁移函数
- 接入流程：在 `verify_and_set_master_key` 之后调一次 `migrate_encrypt_existing_sensitive_fields`，
  并在 `migration::run_migrations` 注册版本号防止重复执行

### 兼容性矩阵（A1 实施后）

| 场景 | 行为 | 风险 |
|---|---|---|
| 新 → 新（双端均 ≥ 7b36af88 + 含本修复）| 字段级 ENC:V3 写入，V3 槽能解密 | ✅ |
| 新 ← 老（老客户端写明文，新客户端读）| `is_encrypted` 检测后原样返回 | ✅ |
| 新 → 老（老客户端 < 7b36af88，读新客户端 ENC:V3）| V3 槽缺失 → 空串 | ⚠️ **本方案规避** |
| 老 → 老（双端均 < 7b36af88）| 不影响，本修复未发布 | ✅ |

### 存量明文如何自然收敛

虽然迁移函数未启用，存量明文会随用户日常操作自然收敛：

1. 用户编辑 SSH 连接（改 passphrase、改端口等）→ 触发 `encrypt_params` → 字段级 ENC:V3 写入
2. 证书导入/编辑场景：同样会触发重新加密
3. 用户卸载旧客户端 → 数据目录丢失（与兼容性问题无关）
