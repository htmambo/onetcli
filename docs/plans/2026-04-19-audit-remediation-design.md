# 审查问题收敛修复设计

**目标**

基于上一轮审查结果，在不引入大范围 UI 变更的前提下，先落地一批高收益修复：补上 SSH/SFTP 主机密钥校验、修复 SSH 共享会话竞态、收口 SSH 配置构建重复逻辑，并让 DB 导入事务开关真正生效，同时减少导入导出 SQL 构造重复。

**方案选择**

1. 全量方案：同时引入主机信任管理 UI、指纹确认弹窗、批量导入重构、导出流式化。
   - 优点：一次性把安全和性能体系做完整。
   - 缺点：改动面过大，涉及 UI、状态持久化、交互协议，当前轮次风险最高。

2. 聚焦批次方案。
   - 优点：只改现有架构内的关键点，能在一轮内闭环安全、性能和去重问题。
   - 缺点：主机密钥信任策略先采用 TOFU + `known_hosts`，暂不提供可视化确认与管理入口。

3. 纯重构方案：只做重复逻辑收口和事务开关接通，不碰 SSH 安全行为。
   - 优点：兼容风险最低。
   - 缺点：会把最关键的安全缺口继续留在主干上，不合适。

**推荐方案**

采用方案 2。

## 架构

- 在 `ssh` crate 内新增统一的主机密钥校验辅助逻辑，复用 `russh` 自带的 `known_hosts` 能力，默认采用 TOFU：首次见到主机时写入 `~/.ssh/known_hosts`，后续若指纹变更则拒绝连接。
- 将 `SshParams -> SshConnectConfig` 的转换下沉到 `one-core::storage::models`，由 `terminal`、`sftp_view`、`terminal_view` 统一复用。
- 修正 `SshSessionManager` 的冷启动并发竞态，保证同一个 manager 在并发调用下只建立一条底层 SSH 连接。
- 在 `db::import_export::formats` 层增加共用 helper，统一导出 `SELECT` SQL 构造，并接通 CSV/JSON/TXT 的批量执行路径，让 `use_transaction` 真正驱动底层事务行为。

## 边界

- 本轮不新增主机密钥确认弹窗，不新增设置项，不做 known_hosts 可视化管理。
- 本轮不重做整个 DB 导出链路的流式 API，只先减少重复 SQL 构造，并修正 schema 丢失问题。
- 本轮不改 `db/src/ssh_tunnel.rs` 的配置构建来源，因为它来自数据库连接参数，不是 `SshParams`。

## 风险与取舍

- TOFU 会在首次连接时自动信任主机，安全性明显强于“默认全放行”，但弱于人工确认指纹；这是当前轮次为了低侵入落地做的取舍。
- 将 CSV/JSON/TXT 改为批量 `execute()` 后，错误聚合逻辑需要保持和原先尽量一致，否则会影响导入反馈。
- `SshSessionManager` 在建连阶段持有状态锁会增加等待时间，但能换取单连接语义正确性，收益更高。

## 验证

- 为 SSH 主机密钥校验补单元测试，覆盖首次学习、重复校验通过、指纹变更拒绝。
- 为 `SshSessionManager` 补并发访问回归测试，确保并发冷启动只触发一次 connector。
- 为导入导出 helper 补单元测试，覆盖 schema 参与导出 SQL 构造。
- 运行目标 crate 的测试与 `cargo check`，验证编译和回归。
