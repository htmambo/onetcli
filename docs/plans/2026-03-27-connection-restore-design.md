# 首页连接恢复设计

**目标**

应用退出时保存当前已打开的连接页快照；下次启动时在首页提示是否恢复，并允许用户勾选要恢复的项。

**方案选择**

1. 直接扩展现有 `tab_state.json` 自动恢复链路。
   - 优点：看起来复用最多。
   - 缺点：当前缺少连接页 builder 注册和自定义 `dump()`，会把需求扩展成完整 tab 框架恢复，风险最高。

2. 单独维护“连接恢复快照”，退出时从当前标签页提取恢复元数据，启动后弹窗勾选，再复用首页现有打开入口恢复。
   - 优点：实现面集中，能满足“提示恢复”和“选择恢复”，还能保持对连接页打开逻辑的复用。
   - 缺点：需要新增一套恢复快照模型，并为连接页补最小 `dump()` 元数据。

**推荐方案**

采用方案 2。

## 架构

- 在 `crates/core/src/` 新增连接恢复快照模型，定义恢复项类型、最小恢复元数据和 JSON 持久化格式。
- 为 `TerminalView`、`SftpView`、`DatabaseTabView`、`RedisTabView`、`MongoTabView` 补 `dump()`，只输出恢复所需的最小元数据，不接入 tab builder 自动恢复。
- 在 `OnetCliApp` 退出时同时保存：
  - 原有 `tab_state.json`
  - 新增 `connection_restore_state.json`
- 在 `HomePage` 中加载工作区和连接数据后，延迟弹出恢复对话框；对话框展示当前仍可恢复的项并支持勾选。
- 用户确认后，根据快照里的“恢复类型”调用精确恢复入口，避免被当前 `DatabaseOpenMode` 改写成错误的页类型。

## 数据流

1. 用户正常使用，打开各类连接页。
2. 退出时：
   - `TabContainer::dump()` 汇总标签页状态。
   - 连接页 `dump()` 输出恢复元数据。
   - 新模块过滤出可恢复项并写盘。
3. 启动时：
   - 首页异步加载工作区和连接。
   - 数据就绪后读取恢复快照，过滤无效项。
   - 弹窗展示可恢复项，用户勾选。
4. 恢复时：
   - SSH / Serial / SFTP 直接按实例恢复。
   - Database / Redis / Mongo 按“单连接页”或“工作区页”精确恢复。
   - 完成后清除本次快照，避免重复提示。

## 错误处理

- 快照文件不存在或解析失败：忽略并不弹窗。
- 恢复项指向的连接已删除：过滤掉，不展示。
- 工作区页的活动连接不存在，但工作区内仍有同类型连接：退化为用当前第一个可用连接恢复工作区页。
- 用户选择“跳过”：直接清除快照，本次不恢复。

## 验证

- 为恢复快照模型补充单元测试，覆盖序列化、过滤和构建逻辑。
- 运行 `cargo fmt`、目标 crate 单测和 `cargo check` 验证编译与集成。
