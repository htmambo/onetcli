# 云同步服务端最简方案（账号 + 同步密钥）

生成时间：2026-03-24 16:24:59 +0800

## 1. 最终结论

如果你的目标只是：
- 同一账号在多个平台使用
- 同步内容在每个账户下保持一致
- 不想做复杂设备管理

那么最适合的方案不是“设备授权”，而是：

## 账号登录 + 同步密钥

具体来说：
- **账号**负责确认用户身份
- **同步密钥**负责解锁该账号下的同步内容
- **服务端**只保存账号级配置和账号级同步数据

这意味着：
- 同一 `user_id` 只有一套云端同步数据
- 任意平台只要登录同一账号，并提供正确的同步密钥，就能拿到同一份内容

## 2. 这个方案为什么最合适

因为当前代码本来就已经接近这个模型：
- `main/src/auth.rs` 已经有账号登录
- `user_configs` 已经能保存 `key_verification`
- `sync_data` 已经能保存统一同步内容
- `CloudSyncService::unlock()` 已经能用主密钥解锁同步

换句话说：

> 你现在需要的不是新架构，而是把现有“账号 + 主密钥”明确收敛成最终产品方案。

## 3. 核心设计

## 3.1 账号负责什么
- 注册
- 登录
- 会话恢复
- 找回密码
- 唯一身份标识 `user_id`

实现方式：
- 继续使用 `Supabase Auth`

## 3.2 同步密钥负责什么
- 验证当前设备能否解锁该账号下的同步内容
- 作为同步内容加密/解密的依据
- 保证服务端只存密文，不存明文业务数据

实现方式：
- 继续使用当前 `key_verification + key_version` 模型

## 3.3 服务端负责什么
- 保存账号级密钥验证信息
- 保存账号级同步数据
- 提供 CRUD 和冲突控制

不负责：
- 设备管理
- Pro / Free
- License
- 订阅
- 支付
- 团队共享

## 4. 账户一致性的真正含义

你现在要的是：

### 一个账户 = 一套云端状态

因此最核心的设计原则是：
- 所有同步数据都挂在 `owner_id = 当前 user_id`
- 所有设备只要属于同一账号，就读取同一命名空间
- 是否能读懂这些数据，取决于是否提供了正确同步密钥

这比“每台设备单独授权”更简单，也更符合你的目标

## 5. 数据模型

## 5.1 `user_configs`

用途：
- 保存当前账户的同步密钥验证信息

建议字段：
- `id bigint generated always as identity primary key`
- `user_id uuid not null unique`
- `key_verification text not null`
- `key_version integer not null default 1`
- `updated_at timestamptz not null default now()`

作用：
- 同一账号只允许一条配置记录
- 新设备登录后，先读取这条记录
- 输入正确同步密钥后才允许解锁同步

## 5.2 `sync_data`

用途：
- 保存当前账户的所有同步内容

建议字段：
- `id uuid primary key default gen_random_uuid()`
- `owner_id uuid not null`
- `data_type text not null`
- `encrypted_data text not null`
- `key_version integer not null default 1`
- `checksum text not null default ''`
- `version integer not null default 1`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- `deleted_at timestamptz null`

## 5.3 `data_type` 推荐值
- `connection`
- `workspace`
- `app_settings`

说明：
- `connection` 和 `workspace` 已经符合当前代码模型
- 如果你还想同步“配置项”，建议加 `app_settings`
- 继续用统一 blob 模型，不要拆表

## 5.4 不需要的表
- `device_authorizations`
- `user_subscriptions`
- `teams`
- `team_members`

当前都不是必须项

## 6. 两种可选实现方式

你提到“可以使用账户的密码或者授权密钥”，这两条路都能做，但建议优先级不同。

## 6.1 方案 A：账号密码只登录，单独维护同步密钥

这是**推荐方案**。

### 体验
- 登录账号
- 首次同步时设置一次同步密钥
- 其他设备登录同一账号后，输入同一同步密钥即可同步

### 优点
- 与当前代码最一致
- 改造最小
- 修改登录密码时，不影响同步数据结构
- 同步逻辑与账号认证逻辑解耦

### 缺点
- 用户首次使用需要额外输入一次同步密钥

## 6.2 方案 B：直接用账号密码派生同步密钥

这是**更省交互的方案**，但不是首推。

### 体验
- 用户只登录一次
- 客户端直接用登录密码派生同步密钥
- 不再单独输入同步密钥

### 优点
- 用户操作最少
- 不需要额外维护同步密钥输入流程

### 缺点
- 修改登录密码时，需要处理同步数据的重新加密
- 所有设备都要重新同步解锁状态
- 认证密码和同步密钥完全耦合，后续演进空间更小

## 6.3 方案 C：使用独立授权密钥

如果你更喜欢“授权密钥”这个概念，也可以把它理解为：

### 授权密钥 = 同步密钥

本质上和方案 A 是一回事，只是命名不同。

因此建议产品上统一叫法：
- 面向用户：`同步密钥` 或 `授权密钥`
- 面向实现：`master_key`

## 7. 推荐选择

### 当前最推荐
- **账号登录继续用 Supabase Auth**
- **同步解锁继续用独立同步密钥**

原因很直接：
- 当前代码已经有这套能力
- 服务端只需要两张核心表
- 不需要新增设备表
- 不需要新增设备注册接口
- 不需要改动整体同步架构

## 8. 服务端最小实现清单

## 8.1 必须保留
- `/auth/v1/...`
- `/rest/v1/user_configs`
- `/rest/v1/sync_data`

## 8.2 必须补齐
- `user_configs(user_id)` 唯一约束
- `sync_data.version` 自动递增触发器
- `updated_at` 自动更新时间触发器
- `sync_data` 的 `owner_id` 过滤规则
- `sync_data` 的软删除支持

## 8.3 当前不用做
- 设备注册 RPC
- 设备授权检查 RPC
- 团队 RPC
- 后台服务

## 9. 自动同步流程

## 9.1 首次设备使用
1. 用户登录账号
2. 客户端读取 `user_configs`
3. 如果不存在，则说明该账号第一次开通同步
4. 用户设置同步密钥
5. 客户端生成 `key_verification`
6. 上传 `user_configs`
7. 开始同步 `sync_data`

## 9.2 新设备接入
1. 用户登录同一账号
2. 客户端读取 `user_configs`
3. 用户输入同一个同步密钥
4. 本地校验 `key_verification`
5. 校验通过后解锁同步
6. 拉取 `sync_data`

## 9.3 日常自动同步
建议触发点：
- 登录成功后
- 会话恢复成功后
- 主密钥解锁成功后
- 本地数据有改动时
- 定时轮询时
- 网络恢复时

## 9.4 推荐顺序
1. `user_configs`
2. `app_settings`
3. `workspace`
4. `connection`

## 10. 为什么不需要设备授权

因为你当前要解决的是：
- 同账号多平台
- 内容保持一致

而不是：
- 每台设备独立审批
- 每台设备独立权限
- 设备风控

所以服务端只需要保证：
- 同一账号读取同一份云端状态
- 没有正确同步密钥就无法解锁内容

这就足够了

## 11. 客户端最小改造

如果走当前最推荐的“账号 + 独立同步密钥”，客户端只需要：

### 11.1 保持现有登录流程
- 不需要大改 `auth.rs`

### 11.2 保持现有主密钥流程
- 继续使用 `setup_master_key`
- 继续使用 `unlock`
- 继续使用 `change_master_key`

### 11.3 补充 `app_settings` 同步
- 如果你希望“配置项”也跨端一致，就新增 `app_settings`

### 11.4 优化自动同步时机
- 登录恢复成功后自动尝试同步
- 解锁成功后立即全量同步
- 本地改动后做防抖增量同步

## 12. 验收清单

- 同一账号在 macOS 登录后创建连接
- 同一账号在 Windows 登录并输入相同同步密钥后能拉到该连接
- 修改工作区后另一端能自动同步
- 修改 `app_settings` 后另一端能同步生效
- 修改同步密钥后，云端数据能正确升版本并重新加密
- 没有同步密钥时，即使账号登录成功也不能解锁同步内容

## 13. 一句话落地建议

### 最终推荐方案
- **账号身份**：Supabase Auth
- **同步解锁**：独立同步密钥
- **核心表**：`user_configs` + `sync_data`

### 不推荐现在加的东西
- 设备授权
- 团队能力
- 订阅/支付
- 后台系统

### 产品化表达
- “登录同一账号后，输入同一同步密钥，即可在所有平台保持配置一致”

这就是当前最简单、也最贴近你需求的最终方案。
